- دیتابیس: `NeginPakhsh_WebDev`
- وضعیت: `READ_ONLY`

## نتیجه اصلی: قیمت یک عدد روی کالا نیست

```text

  ├──< SLE.tblPrice   ───── تاریخچه قیمت فروش/مصرف‌کننده کالا

  ├──< tblDiscountPrizeList   جایزه‌های انتخابی
  ├──< tblDisSale             اثر اعمال‌شده روی فروش
  └──< tblOrderPrize          جایزه محاسبه‌شده سفارش
```

توابع رسمی `SLE.FindGoodsPrice*` چهار Source متفاوت را تشخیص می‌دهند: قیمت
خرید، قیمت قراردادی فروش، تاریخچه قیمت فروش و قیمت مصرف‌کننده. بنابراین
`Product.price` یا «آخرین قیمت» به‌تنهایی مدل قابل‌قبولی برای وب‌ERP نیست.

## ترتیب انتخاب قیمت

شواهد توابع فعلی:

1. تاریخ عملیات باید داخل `StartDate..EndDate` باشد.
2. کالا می‌تواند مستقیم یا از GoodsGroup/MainType/SubType انتخاب شود.
3. شرط‌های مشتری، Category، Activity، Level، جغرافیا، نوع پرداخت، مهلت، نوع
   سفارش، دسته فروشنده، Batch، دفتر فروش و ارز می‌توانند در انتخاب نقش داشته
   باشند.
4. در بعضی مسیرها ردیف با GoodsRef مستقیم قبل از گروه و سپس `Priority` مرتب
   می‌شود؛ در مسیرهای دیگر StartDate یا DC نیز وارد ترتیب شده است.
5. چند تابع قدیمی قواعد یکسانی ندارند؛ برای مثال نسخه‌های `FindGoodsPrice`،
   `FindGoodsPriceRef` و `FindGoodsPriceWithDC` شرط‌های کاملاً یکسان ندارند.

در نتیجه باید قبل از پیاده‌سازی Engine جدید، Golden Test روی چند سفارش واقعی
ساخته شود و نتیجه هر مسیر با وارانگار مقایسه شود؛ یکی‌کردن توابع صرفاً از روی
ظاهر SQL مجاز نیست.

## Header تخفیف و جایزه

`SLE.tblDiscount` تعداد ۵٬۰۹۸ Rule با ۵٬۰۶۶ کد متمایز، ۵٬۰۹۸ UUID یکتا و
۵۵۳ گروه تخفیف دارد. کد Rule یکتا نیست: ۳۲ گروه کد تکراری وجود دارد.

Master هدف Rule سه مقدار دارد:

- ۱: تخفیفات و جوایز؛
- ۲: عدم فروش؛
- ۳: قوانین محاسبه مهلت پرداخت.

در داده فعلی ۵٬۰۶۸ Rule نوع اول و ۳۰ Rule نوع دوم هستند؛ Rule نوع سوم در این
جدول مصرف نشده، اما Master معتبر است.

`IsActive=1` برای ۳٬۷۸۶ Rule ثبت شده، ولی در تاریخ `۱۴۰۵/۰۶/۰۴` فقط ۸۵۴
Rule واقعاً مؤثرند. ۲٬۹۳۲ Rule هنوز Flag فعال دارند اما تاریخشان منقضی شده؛
۱٬۳۱۲ Rule نیز بی‌اثر شده‌اند. پس وضعیت UI باید از ترکیب Flag و بازه تاریخ
محاسبه شود:

```text
effective = IsActive=1 AND StartDate<=today
            AND (EndDate IS NULL OR EndDate>=today)
```

جدول Log تعداد ۱٬۳۱۳ رویداد تغییر به حالت غیرفعال دارد؛ رویداد تغییر به فعال
در Snapshot وجود ندارد. این Log را نباید به‌تنهایی تاریخچه کامل Status دانست.

## Crosswalk با NGT

- ۱۴٬۷۸۸ Promotion خط NGT همگی `DiscountRef` عددی قابل تبدیل و منطبق با
  `tblDiscount.ID` دارند؛ `DiscountAmount` همه قابل Parse است.
- ۱۰۷٬۴۹۰ جایزه سفارش NGT همگی `DisRef` عددی معتبر و UUID کالای معتبر دارند.
- فقط ۴۰٬۳۴۰ ردیف UUID تخفیف منطبق دارند؛ ۶۷٬۱۵۰ ردیف UUID صفر دارند.
- در ردیف‌های دارای UUID معتبر، ID و UUID به یک Rule اشاره می‌کنند.
- هر ۹۱۸ جایزه تحقق‌یافته فروش با Rule، کالا و Sale معتبر تطبیق دارد.

پس در تاریخچه NGT، `DisRef` عددی شاهد کامل‌تری از UUID است. UUID صفر رکورد را
باطل نمی‌کند؛ در مدل مقصد باید Source ID و Source UUID جدا حفظ و کیفیت Crosswalk
علامت‌گذاری شود.

- Price، CPrice، Unit، DiscountGoods و PrizeList ارجاع کالای یتیم ندارند.
- ۱۰ شرط برای ۸ DiscountRef حذف‌شده/تاریخی وجود دارد. چون FK Header تعریف

- زوج Rule/Goods و Rule/Prize تکراری نیست.
- ۴۰ کالا Price مؤثر و ۲۶۷ کالا CPrice مؤثر ندارند؛ این لزوماً خطا نیست، اما

- ۲۷۱ Price و ۱۳٬۷۸۰ CPrice بازه معکوس دارند و باید به‌عنوان تاریخچه Close/

- `ProductPriceHistory` برای Sale/User/Manufacturer/Supplier price؛
- `ContractPriceRule` با بازه اعتبار، Currency و Priority پایدار؛
- `ContractPriceCondition` چندمقداری و نوع‌دار؛
- `CommercialRule` برای Discount/Prize/NoSale/PaymentUsance؛
- `CommercialRuleScope` برای Line/Group/Order؛
- `CommercialRuleCondition` برای مشتری، کانال، جغرافیا، پرداخت و سفارش؛
- `CommercialRuleProductSelector` برای کالا/گروه/برند/نوع؛
- `CommercialRuleResult` برای درصد، مبلغ، Addition، Single/Selectable/Basket

- `AppliedCommercialRule` غیرقابل‌تغییر روی سفارش/فاکتور؛
- `AppliedPrize` با کالا، مقدار، Auto/Manual و Rule source؛
- `RuleStatusHistory` و `RuleEvaluationTrace`؛
- `MigrationQuarantine` برای شرط یتیم، UUID صفر و ردیف بدون CPrice؛
- `GoldenCase` برای ورودی و خروجی مورد انتظار موتور قدیمی.

## قواعد قطعی برای وب‌ERP

1. قیمت نمایش داده‌شده باید Context مشتری، نوع سفارش، تاریخ، واحد و سایر شروط
   را دریافت کند؛ API بدون Context فقط «قیمت عمومی محدود» می‌دهد.
2. Rule فعال فقط با Flag تعیین نمی‌شود؛ تاریخ جزء قرارداد است.
3. Rule ID، Code، UUID و Group چهار شناسه متفاوت‌اند.
4. Discount، Addition، Prize و NoSale نتیجه‌های متفاوت‌اند.
5. Rule محاسبه‌شده همراه سند Snapshot می‌شود؛ تغییر Master نباید سند گذشته را
   دوباره محاسبه کند.
6. `SqlCondition` قدیمی مستقیماً اجرا نمی‌شود.
7. Priority از Float قدیمی به ترتیب پایدار و تست‌شده تبدیل می‌شود.
8. هیچ Rule یا قیمت بدون مقایسه Golden Case با وارانگار منتشر نمی‌شود.

## Golden Caseهای لازم

1. قیمت مستقیم کالا و fallback گروه؛
2. دو Rule هم‌اولویت با specificity متفاوت؛
3. Rule فعال ولی منقضی؛
4. Discount و Addition هم‌زمان؛
5. Prize خودکار و انتخابی؛
6. NoSale rule؛
7. UUID صفر NGT با Source ID معتبر؛
8. سفارش تاریخی که Snapshot آن پس از تغییر Master ثابت می‌ماند؛
9. یک Order line بدون CPriceRef در Reconciliation queue.

## ابهام‌های باز

- برچسب رسمی `CPriceType=1/5`؛
- تفاوت دقیق خانواده‌های `DisType=11/21`؛
- ترتیب نهایی Tie-break میان Priority، specificity، StartDate و DC در همه
  مسیرهای سفارش؛
- الگوهای ۸۴۵ `SqlCondition` و طراحی DSL امن جایگزین؛
- علت ۹۲ کالای View عمومی در برابر ۳٬۵۵۷ کالای Contract مؤثر؛
- Reconciliation یک سفارش بدون CPriceRef و هشت Rule حذف‌شده دارای Condition؛
- Golden Dataset قیمت/تخفیف از سفارش‌های واقعی سه‌ماهه.
