## فروش و سفارش

از ۳۸٬۰۶۳ سفارش:

- ۳۰٬۱۳۳ سفارش به فروش نهایی فعال رسیده‌اند؛
- ۲٬۲۱۴ سفارش Sale voucher فعال بدون شماره نهایی دارند؛
- ۳٬۸۲۶ سفارش به Sale منتخب لغوشده وصل‌اند؛
- ۱٬۸۴۸ خود سفارش لغوشده‌اند؛
- ۴۲ سفارش تأییدشده هنوز Sale ندارند.

در همان پنجره بر پایه `SaleDate`، تعداد ۴۰٬۰۵۹ Sale برای ۳۶٬۷۷۳ سفارش دیده
می‌شود: ۳۲٬۳۵۷ فعال و ۷٬۷۰۲ لغوشده. بیشتر بودن Sale از Order نتیجه چند تلاش و
تفاوت تاریخ دو سند است؛ UI مقصد نباید رابطه را یک‌به‌یک فرض کند.

Typeهای اصلی سفارش: پیش‌ویزیت ۲۰٬۰۲۹، پیش‌ویزیت تهران ۸٬۱۰۴، رسمی عادی
۳٬۶۵۱ و پیش‌ویزیت گیلان ۲٬۵۴۷. بنابراین Previsit هسته واقعی عملیات فروش است،
نه قابلیت فرعی.

## کالا، قیمت و Rule

- ۲٬۳۳۶ کالا حداقل یک فعالیت سفارش/فروش/انبار داشته‌اند؛
- ۲٬۰۹۲ کالا در سفارش، ۲٬۰۹۰ در فروش و ۲٬۳۳۰ در انبار فعال بوده‌اند؛
- ۱٬۴۸۸ کالا هیچ فعالیتی نداشته‌اند؛
- ۲۰۲٬۵۳۵ Order line، ۲۶۱٬۴۷۱ Sale line و ۲۰۲٬۶۳۸ Inventory line ثبت شده؛
- ۱٬۴۴۱ کالای `ShowInSale=1` بدون فعالیت و ۴۰۵ کالای با Flag مخالف ولی دارای
  فعالیت وجود دارد؛ Flag نمایش معادل وضعیت فعالیت نیست.

در Lineهای معتبر Rule:

- ۲۰۱٬۸۶۵ Sale line همگی `CPriceRef` دارند؛
- ۱۹۳٬۱۲۲ Order line وجود دارد و فقط یک مورد `CPriceRef` ندارد؛
- ۱۵۷٬۷۰۰ Sale line تخفیف و ۱۳۸٬۰۵۴ Line مبلغ اضافه دارند؛
- ۳۰۰٬۳۶۱ اثر Rule روی ۲۹٬۰۵۳ Sale و ۷۰۴ Rule دیده شد؛
- ۹٬۷۴۰ Prize line در ۱٬۰۲۰ سفارش ثبت شد.

این حجم استفاده، Price/Discount engine را جزء Slice فروش می‌کند؛ پیاده‌سازی یک
فیلد قیمت و درصد تخفیف ثابت، Parity نخواهد داشت.

## نتیجه برای ترتیب ساخت وب

1. Foundation باید کاتالوگ، مشتری/پرسنل، Scope مجوز و Config resolver را بدهد.
2. اولین جریان عملیاتی باید Previsit/Order → Price/Rule → Sale باشد.
3. Inventory reservation/exit و Distribution بلافاصله پس از آن لازم‌اند.
4. Receipt/Allocation/Cheque و Return باید Ledger مستقل و Projection مانده داشته
   باشند.
5. Purchase/Payable بدون Supplier cardex چندمنبعی ناقص است.
6. هر Domain command باید Posting crosswalk تا Journal و Reconciliation سه‌لایه
   داشته باشد.
